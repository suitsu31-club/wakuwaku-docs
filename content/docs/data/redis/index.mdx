Redis is where a microservice keeps the state that is shared between replicas but doesn't belong in the primary database: cached reads, locks, rate-limit counters, messages on their way to a websocket, the chunks of a streamed LLM answer. The `redis` feature of wakuwaku turns Redis into a [data source](/en/docs/data/queries) like PostgreSQL: every command is a typed query, and a `Db` handle only runs the queries its capability allows.

On top of the data source, wakuwaku ships ready-made data structures, each one a small `const` value whose methods build queries:

| Structure | Module | Use it for |
| --- | --- | --- |
| [`Cache`, `HashedCache`](/en/docs/data/redis/cache) | `collection::cache` | Bodies with a TTL; the hashed variant answers "has it changed?" without downloading the body. |
| [`Lock`, `RwLock`](/en/docs/data/redis/lock) | `collection::lock` | Mutual exclusion across replicas, with leases. |
| [`TokenBucket`](/en/docs/data/redis/rate-limiter) | `collection::token_bucket_limiter` | Rate limiting with bursts. |
| [`Promise`](/en/docs/data/redis/promise) | `dynamic::promise` | A value completed once and waited on by anyone, like a `oneshot` across replicas. |
| [`Watch`](/en/docs/data/redis/watch) | `dynamic::watch` | The latest version of some state, waited on for newer ones, like a `watch` channel across replicas. |
| [`Pipe`](/en/docs/data/redis/pipe) | `dynamic::pipe` | A one-way, one-receiver message queue, like one direction of a websocket. |
| [`LiveView`](/en/docs/data/redis/live-view) | `dynamic::live_view` | A durable document with versioned commits that subscribers follow as diffs. |
| [`StreamBuffer`](/en/docs/data/redis/stream-buffer) | `dynamic::stream_buffer` | An append-only array with an end, followed by any number of subscribers. |

The *collections* are queried on demand. The *dynamic* structures can also be waited on as they change, through one [watch hub](#following-changes-the-watch-hub) per process.

If you come from Spring, this page covers what Spring Data Redis' connection setup does, and the subpages replace the usual mix of `RedisCacheManager`, a distributed lock registry and a rate-limiting library, with one typing discipline across all of them.

## Setup

Enable the `redis` feature. Bodies stored in Redis are serialized with [kanau](https://docs.rs/kanau)'s `MessageSer` / `MessageDe`; the JSON derives need a direct `kanau` dependency with its `serde_json` feature, plus `serde`:

```toml title="Cargo.toml"
[dependencies]
wakuwaku = { version = "1.0.0-rc4", features = ["redis"] }
kanau = { version = "0.6", features = ["serde_json"] }  # JsonMessageSer / JsonMessageDe
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
```

Cargo unifies this `kanau` with the one wakuwaku uses, so `wakuwaku::deps::kanau` and `kanau` are the same crate. See [Serializing the body](/en/docs/events/defining-events#serializing-the-body) for how the derives work and how to write `MessageSer` / `MessageDe` by hand instead.

The Redis client itself is re-exported as `wakuwaku::deps::redis`, so you don't add `redis` to `Cargo.toml`.

### Connecting

A [`RedisSource`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/redis/struct.RedisSource.html) wraps a cloneable async connection and runs each query on a clone of it. With the default `MultiplexedConnection` the clones share one socket, so this is cheap. Wrap the source in a `Db` with a capability:

```rust title="src/redis.rs"
use wakuwaku::deps::redis;
use wakuwaku::entity::redis::RedisSource;
use wakuwaku::entity::{Db, ReadWrite};

/// The Redis handle every component of this service shares.
pub type Redis = Db<RedisSource, ReadWrite>;

pub async fn connect(client: &redis::Client) -> redis::RedisResult<Redis> {
    let connection = client.get_multiplexed_async_connection().await?;
    Ok(Db::new(RedisSource::new(connection)))
}
```

`RedisSource<C>` accepts any `C: ConnectionLike + Clone + Send + Sync`, so a cluster connection or a `ConnectionManager` works the same way.

### Registering it

`Db` is `Clone` whenever its source is, so register it in the [`ServiceBuilder`](/en/docs/core/service-builder) and build components from it:

```rust title="src/main.rs"
use wakuwaku::{ServiceBuilder, ServiceCreation};

pub struct SessionService {
    redis: Redis,
}

impl ServiceCreation for SessionService {
    type Dep = Redis;

    fn create_service(redis: Redis) -> Self {
        Self { redis }
    }
}

pub async fn run() -> Result<(), Box<dyn std::error::Error>> {
    let client = redis::Client::open("redis://127.0.0.1/")?;
    let services = ServiceBuilder::new(connect(&client).await?);
    let redis: &Redis = services.provide::<Redis, _>();
    Ok(())
}
```

Every query of this section is then run with `redis.process(query).await`, the [`Processor`](https://docs.rs/kanau) method that `Db` implements for each query its capability covers.

## Your own Redis queries

The built-in structures are queries like any other. When you need a command they don't cover, write the query yourself: [`Query`](/en/docs/data/queries) declares which entity it touches, and `Execute<RedisSource<C>>` runs it on the connection.

```rust title="src/session.rs"
use wakuwaku::deps::redis::aio::ConnectionLike;
use wakuwaku::deps::redis::{self, AsyncCommands};
use wakuwaku::entity::redis::RedisSource;
use wakuwaku::entity::{Entity, Execute, Query, Write};

/// The entity: login sessions, wherever they are stored.
pub struct Session;
impl Entity for Session {}

pub struct StoreSession {
    pub token: String,
    pub user: u64,
}

impl Query for StoreSession {
    type Effect = Write<Session>;
}

impl<C: ConnectionLike + Clone + Send + Sync> Execute<RedisSource<C>> for StoreSession {
    type Output = ();
    type Error = redis::RedisError;

    async fn execute(self, conn: &mut C) -> redis::RedisResult<()> {
        conn.set_ex(format!("session:{}", self.token), self.user, 3600).await
    }
}
```

Every query declares its error type. It must convert from `RedisError`, the error of `RedisSource`, so a failure to talk to Redis can always be reported. The built-in structures use `RedisError` itself, and also report a body that fails to (de)serialize, and a key whose contents don't match what the structure wrote (`"corrupted item"`), as a `RedisError`.

### Queries that can refuse

A query that can refuse on its own, because a seat is already taken or a business rule says no, declares its own error type instead. The refusal then reaches the caller as an `Err` next to the Redis failures, and a single `?` handles both:

```rust title="src/seat.rs"
use wakuwaku::deps::redis::aio::ConnectionLike;
use wakuwaku::deps::redis::{self, AsyncCommands};
use wakuwaku::entity::redis::RedisSource;
use wakuwaku::entity::{Entity, Execute, Query, Write};

pub struct Seat;
impl Entity for Seat {}

#[derive(Debug)]
pub enum ClaimError {
    /// Someone else holds the seat.
    Taken,
    Redis(redis::RedisError),
}

impl From<redis::RedisError> for ClaimError {
    fn from(error: redis::RedisError) -> Self {
        Self::Redis(error)
    }
}

pub struct ClaimSeat {
    pub seat: u32,
    pub user: u64,
}

impl Query for ClaimSeat {
    type Effect = Write<Seat>;
}

impl<C: ConnectionLike + Clone + Send + Sync> Execute<RedisSource<C>> for ClaimSeat {
    type Output = ();
    type Error = ClaimError;

    async fn execute(self, conn: &mut C) -> Result<(), ClaimError> {
        let claimed: bool = conn.set_nx(format!("seat:{}", self.seat), self.user).await?;
        if claimed { Ok(()) } else { Err(ClaimError::Taken) }
    }
}
```

`redis.process(ClaimSeat { seat, user }).await` then outputs `Result<(), ClaimError>`: no `Result` nested in the output, and no separate check after the query.

## Names and keys

Each structure is generic over the type `N` that names its items: `Cache<u64, Profile>` is keyed by user ID, `Lock<str>` by a string. A name must implement [`Name`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/redis/trait.Name.html), which strings, byte strings and every integer type already do. For an identifier newtype, write its canonical form:

```rust
use wakuwaku::entity::redis::Name;

pub struct UserId(pub u64);

impl Name for UserId {
    fn write_name(&self, key: &mut Vec<u8>) {
        self.0.write_name(key);
    }
}
```

An item lives under the key

```text
@@wakuwaku-entity:<kind>:<namespace>:<name>
```

where `<kind>` is the structure type (`Cache`, `Lock`, `TokenBucket`, …) and `<namespace>` is the first argument of its `new`. Items made of several keys (`RwLock`, `Pipe`, `LiveView`) wrap `<namespace>:<name>` in braces and append a suffix per key, so all their keys share one Redis Cluster hash slot and their Lua scripts and `MULTI` blocks work on a cluster.

<Callout type="warn" title="One namespace per structure">
  Two structures of the same kind with the same namespace share their keys. `Cache<u64, Profile>` and `Cache<u64, Settings>` both named `"user"` would overwrite each other's bodies and then fail to deserialize them. Give each `const` its own namespace.
</Callout>

## Capabilities

Each structure type is also the [entity](/en/docs/data/queries) its queries read and write, so `Cache<u64, Profile>` and `Cache<str, Page>` are different entities. Which queries count as writes follows what they do in Redis, not what they look like:

| Structure | Read queries | Write queries |
| --- | --- | --- |
| `Cache` | `get` | `put`, `remove` |
| `HashedCache` | `get`, `hash`, `get_if_changed` | `put`, `remove` |
| `Lock` | | `try_lock`, `release`, `extend` |
| `RwLock` | | `try_read`, `try_write`, `release`, `extend` |
| `TokenBucket` | | `acquire`, `reset` |
| `Promise` | `get`, `wait` | `complete`, `remove` |
| `Watch` | `get`, `changed` | `publish`, `remove` |
| `Pipe` | | `send`, `close`, `receive` (taking a message removes it) |
| `LiveView` | `get`, `version`, `history`, `subscribe`, `resume` | `create`, `commit`, `remove` |
| `StreamBuffer` | `read`, `subscribe` | `append`, `finish`, `remove` |

A `Db<_, ReadOnly>` therefore can't take a lock or consume a rate-limit token, and putting a body through it doesn't compile:

```rust
use wakuwaku::deps::kanau::processor::Processor;
use wakuwaku::deps::redis::RedisResult;
use wakuwaku::entity::redis::RedisSource;
use wakuwaku::entity::{Db, ReadOnly};

async fn warm(replica: &Db<RedisSource, ReadOnly>, user: u64, profile: Profile) -> RedisResult<()> {
    // error: `ReadOnly: CanWrite<Cache<u64, Profile>>` is not satisfied
    replica.process(PROFILES.put(&user, profile)).await
}
```

A capability can also grant access to some structures only. This gateway reads every cache but writes only the session cache:

```rust
use wakuwaku::entity::redis::collection::cache::Cache;
use wakuwaku::entity::{CanRead, CanWrite};

pub struct SessionToken(String);
pub struct Session {
    user: u64,
}

/// Reads every cache, writes only the session cache.
pub enum Gateway {}
impl<N: ?Sized, B> CanRead<Cache<N, B>> for Gateway {}
impl CanWrite<Cache<SessionToken, Session>> for Gateway {}
```

## Following changes: the watch hub

Waiting on a promise or a watch, receiving from a pipe and subscribing to a live view or a stream buffer are queries too, so the capability is checked as usual. None of them blocks a connection. A wait reads the item with ordinary commands on your `RedisSource` connection and, when there is nothing new yet, sleeps until the process's [`WatchHub`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/redis/watch_hub/struct.WatchHub.html) wakes it.

The hub plays the part of the reactor in an async runtime. Every write to a dynamic structure publishes a wake-up on the item's channel, in the same Lua script as the write. The hub listens to the channels its waits need on one Pub/Sub connection, so a thousand pending waits still cost one connection. Connect one per process when the service starts:

```rust title="src/main.rs"
use wakuwaku::ServiceBuilder;
use wakuwaku::deps::redis;
use wakuwaku::entity::redis::watch_hub::WatchHub;

pub async fn run() -> Result<(), Box<dyn std::error::Error>> {
    let client = redis::Client::open("redis://127.0.0.1/")?;
    let hub = WatchHub::connect(client.clone()).await?;
    let services = ServiceBuilder::new(connect(&client).await?).push(hub);
    let hub: &WatchHub = services.provide::<WatchHub, _>();
    Ok(())
}
```

`WatchHub` is cheap to clone, so components keep their own clone and pass `&hub` to each wait. `connect` fails if the first connection fails; later failures are retried.

Why waits never miss a change:

- **Subscribe, then read.** A wait subscribes to its item before its first read, and reads again after every wake-up. A change committed before the subscription is visible to the read; a change after it sends a wake-up.
- **Wake-ups are hints.** They carry nothing, and the wait always reads the item itself. An extra wake-up only costs one read.
- **Shared subscriptions.** Waits on the same item share one subscription, which the last one to finish removes.
- **Reconnects.** When the connection drops, or stops answering the pings sent every 15 seconds, the hub reconnects with a backoff, resubscribes, and wakes every wait so it reads what it missed. A wait whose deadline passes meanwhile reads once more before it gives up.

The hub's task stops once every clone of the hub and every wait using it has been dropped.

Each receiver and subscription has an `async fn recv` and an `into_stream` that turns it into a `futures::Stream`. Promises and watches are waited on with a single query and a timeout instead; [Waiting for asynchronous work](/en/docs/guides/waiting-for-async-work) explains when to use which.

## Server requirements

- Locks and the rate limiter read the server clock with `TIME` inside Lua scripts. This needs effects replication of scripts, the default since Redis 5. Because the clock is the server's, clock skew between your replicas doesn't matter.
- Waits use Pub/Sub: writers `PUBLISH` from Lua scripts, and the hub `SUBSCRIBE`s. Each item's channel has the same name as one of its keys, so with ACLs, grant the hub's user the channels `@@wakuwaku-entity:*` as well as the keys.
- Structures that span several keys keep them in one hash slot, so Redis Cluster is supported. Writers use plain `PUBLISH`, which the cluster forwards to every node, so connect the hub to any one node.
