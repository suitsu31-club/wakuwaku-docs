This page builds the data access of a small user service on PostgreSQL. It defines queries, builds a primary handle and a replica handle, sends each query to the right one, and registers the handles in the [`ServiceBuilder`](/en/docs/core/service-builder). The concepts behind it (entities, capabilities, effects) are explained in the [overview](/en/docs/data).

## Setup

```toml title="Cargo.toml"
[dependencies]
wakuwaku = { version = "1.0.0-rc2", features = ["sqlx-pg"] }
tokio = { version = "1", features = ["full"] }
```

`sqlx-pg` enables `wakuwaku::entity` with the PostgreSQL data source, and re-exports sqlx as `wakuwaku::deps::sqlx`.

## Define the entities

```rust title="src/entities.rs"
use wakuwaku::entity::Entity;

/// The `users` table.
pub struct User;
impl Entity for User {}

/// The `posts` table.
pub struct Post;
impl Entity for Post {}
```

## Define a query

A query implements two traits:

- [`Query`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/query/trait.Query.html) says **what it touches**: its `Effect`. This part doesn't depend on where the query runs, so capability checks and [hooks](/en/docs/data/hooks) work the same for every data source.
- [`Execute<S>`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/query/trait.Execute.html) says **how it runs** on the data source `S`: its `Output`, its `Error`, and the code that runs on a connection. A query written in portable SQL may implement it for several sources.

```rust title="src/queries.rs"
use crate::entities::{Post, User};
use wakuwaku::deps::sqlx::{self, PgConnection};
use wakuwaku::entity::sqlx::backend::PgSource;
use wakuwaku::entity::{Execute, Query, Read, Write};

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct UserRow {
    pub id: i64,
    pub name: String,
}

/// Load one user by id.
pub struct FindUser {
    pub id: i64,
}

impl Query for FindUser {
    type Effect = Read<User>;
}

impl Execute<PgSource> for FindUser {
    type Output = Option<UserRow>;
    type Error = sqlx::Error;

    async fn execute(self, conn: &mut PgConnection) -> Result<Option<UserRow>, sqlx::Error> {
        let row: Option<(i64, String)> = sqlx::query_as("SELECT id, name FROM users WHERE id = $1")
            .bind(self.id)
            .fetch_optional(conn)
            .await?;
        Ok(row.map(|(id, name)| UserRow { id, name }))
    }
}
```

`execute` receives a plain `&mut PgConnection` and returns the query's `Error`. A query that can only fail the way the database fails uses the data source's error, `sqlx::Error` for sqlx sources; a query that can also refuse on its own declares [its own error type](#own-error-type). When the query runs on its own, the connection comes from the pool in autocommit mode. Inside a [transaction](/en/docs/data/transactions), it is the transaction's connection. The same query works in both places.

A query that touches several entities lists them all. A tuple is the union of its effects:

```rust title="src/queries.rs"
/// Titles of the posts of an active author.
pub struct PostsByAuthor {
    pub author: i64,
}

impl Query for PostsByAuthor {
    // Reads two tables: a tuple is the union of its effects.
    type Effect = (Read<User>, Read<Post>);
}

impl Execute<PgSource> for PostsByAuthor {
    type Output = Vec<String>;
    type Error = sqlx::Error;

    async fn execute(self, conn: &mut PgConnection) -> Result<Vec<String>, sqlx::Error> {
        sqlx::query_scalar(
            "SELECT p.title FROM posts p JOIN users u ON u.id = p.author_id \
             WHERE u.id = $1 AND u.active ORDER BY p.created_at DESC",
        )
        .bind(self.author)
        .fetch_all(conn)
        .await
    }
}
```

A write declares `Write<E>`. A capability that can write `E` can also read it, so `Write<User>` is enough for an `UPDATE` that also filters on `users`:

```rust title="src/queries.rs"
/// Change a user's display name.
pub struct RenameUser {
    pub id: i64,
    pub name: String,
}

impl Query for RenameUser {
    type Effect = Write<User>;
}

impl Execute<PgSource> for RenameUser {
    /// Rows affected.
    type Output = u64;
    type Error = sqlx::Error;

    async fn execute(self, conn: &mut PgConnection) -> Result<u64, sqlx::Error> {
        let done = sqlx::query("UPDATE users SET name = $2 WHERE id = $1")
            .bind(self.id)
            .bind(self.name)
            .execute(conn)
            .await?;
        Ok(done.rows_affected())
    }
}
```

<Callout type="info" title="Declare honestly">
The compiler checks the effect you declare, not the SQL you write. A query declared as `Read<User>` that runs an `UPDATE` still compiles. Treat the `Effect` line like a function signature and review it together with the statement.
</Callout>

## Data sources

A [`DataSource`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/query/trait.DataSource.html) is anything that can run queries: a connection pool, a multiplexed client. It fixes the connection type that queries receive and its own error type, which every query's `Error` must be convertible from:

```rust
pub trait DataSource: Send + Sync + Sized {
    type Connection: Send;
    type Error: Send;

    fn run<Q: Execute<Self>>(
        &self,
        query: Q,
    ) -> impl Future<Output = Result<Q::Output, Q::Error>> + Send;
}
```

`run` returns the query's own result. If the source fails before the query starts, for example because no connection could be acquired, that error is converted into `Q::Error` through `From<Self::Error>`.

You rarely implement it yourself. wakuwaku provides one per backend:

| Source | Feature | Connection | Source error |
|---|---|---|---|
| `entity::sqlx::backend::PgSource` | `sqlx-pg` | `PgConnection` | `sqlx::Error` |
| `entity::sqlx::backend::MySqlSource` | `sqlx-mysql` | `MySqlConnection` | `sqlx::Error` |
| `entity::redis::RedisSource` | `redis` | see [Redis](/en/docs/data/redis) | `redis::RedisError` |
| `entity::meilisearch::MeiliSource` | `meilisearch` | see [Meilisearch](/en/docs/data/meilisearch) | `meilisearch_sdk::errors::Error` |

`PgSource` is an alias for `SqlxSource<Postgres>`. Each query run on its own acquires a connection from the pool.

## Build the handles

A `Db<S, C>` owns a data source `S` and has a capability `C`. The capability is only a type parameter, so you choose it when you build the handle. A service with a primary and a read replica builds two handles:

```rust title="src/wiring.rs"
use crate::queries::{
    DeactivateUsers, DormantUsers, EditPostError, EditPostTitle, FindUser, PostsByAuthor, RenameUser, UserRow,
};
use std::time::Duration;
use wakuwaku::deps::kanau::processor::Processor;
use wakuwaku::deps::sqlx::{self, postgres::PgPoolOptions};
use wakuwaku::entity::sqlx::backend::{PgSource, SqlxSource};
use wakuwaku::entity::{Db, ReadOnly, ReadWrite};
use wakuwaku::{CronJob, CronJobInterval, CronTick, ServiceBuilder};

/// The two handles of the service: writes go to the primary,
/// reads that tolerate replication lag go to the replica.
#[derive(Clone)]
pub struct Databases {
    pub primary: Db<PgSource, ReadWrite>,
    pub replica: Db<PgSource, ReadOnly>,
}

impl Databases {
    pub async fn connect(primary_url: &str, replica_url: &str) -> Result<Self, sqlx::Error> {
        let primary = PgPoolOptions::new().max_connections(10).connect(primary_url).await?;
        let replica = PgPoolOptions::new().max_connections(20).connect(replica_url).await?;
        Ok(Self {
            primary: Db::new(SqlxSource::new(primary)),
            replica: Db::new(SqlxSource::new(replica)),
        })
    }
}
```

<Callout type="warn" title="The type is the promise">
`Db::new` can't tell which server a pool is connected to. Building a `Db<PgSource, ReadWrite>` from the replica pool compiles, and it would then send writes to the replica. Only build a writing capability from a source connected to a writable database, and keep this wiring in one place.
</Callout>

Once a pool is wrapped, you can't get it back out of the handle. That is what makes the capability sound. Run migrations and other setup on the pool before calling `SqlxSource::new`. Cloning a `Db` clones its source, and for sqlx that means cloning the pool handle, which is cheap.

## Run a query

`Db` implements kanau's [`Processor`](https://docs.rs/kanau/latest/kanau/processor/trait.Processor.html). Bring the trait into scope and call `process`:

```rust title="src/wiring.rs"
pub async fn run_one(dbs: &Databases) -> Result<(), sqlx::Error> {
    let user: Option<UserRow> = dbs.replica.process(FindUser { id: 7 }).await?;
    let renamed: u64 = dbs.primary.process(RenameUser { id: 7, name: "Haruki".into() }).await?;
    println!("{user:?}, {renamed} row(s) updated");
    Ok(())
}
```

`process` returns the query's `Output`, or the query's `Error`.

## Keep handlers generic over the handle

Handlers shouldn't name `Db<PgSource, ReadOnly>`. They should list the queries they need as `Processor` bounds:

```rust title="src/wiring.rs"
pub struct Profile {
    pub user: UserRow,
    pub posts: Vec<String>,
}

/// Works with any handle that can run both queries.
pub async fn load_profile<D>(db: &D, id: i64) -> Result<Option<Profile>, sqlx::Error>
where
    D: Processor<FindUser, Output = Option<UserRow>, Error = sqlx::Error>
        + Processor<PostsByAuthor, Output = Vec<String>, Error = sqlx::Error>,
{
    let Some(user) = db.process(FindUser { id }).await? else {
        return Ok(None);
    };
    let posts = db.process(PostsByAuthor { author: id }).await?;
    Ok(Some(Profile { user, posts }))
}

pub async fn rename_user<D>(db: &D, id: i64, name: String) -> Result<bool, sqlx::Error>
where
    D: Processor<RenameUser, Output = u64, Error = sqlx::Error>,
{
    Ok(db.process(RenameUser { id, name }).await? == 1)
}
```

The capability is then checked once, where the handle is passed in. This also means:

- A handler accepts any processor of its queries: a `Db`, a `Db` wrapped in [write hooks](/en/docs/data/hooks), or a fake in a [unit test](/en/docs/core/testing).
- With several `Processor` bounds, pin `Output` and `Error` in each bound as above, so that `db.process(...)` has an unambiguous result type.

## A query's own error type [#own-error-type]

Some queries can fail for reasons of their own, not only because the database failed. An update guarded by an optimistic lock finds that someone else changed the row first; a withdrawal would overdraw the account. Such a refusal is a failure of the operation, so it belongs in the query's `Error`, not in its `Output`.

Putting it in the `Output` (`Output = bool`, or `Output = Result<Post, Conflict>`) works, but every caller then has to check the result a second time after the `?`, and a caller that forgets compiles fine and treats the refusal as success. With its own error type, the refusal travels like any other error: `?` propagates it and a `match` handles it.

The only requirement is `type Error: From<S::Error>`, so that the data source's errors fit into it. Here a `posts` row carries a `version` column, and an edit applies only to the version the client last read:

```rust title="src/queries.rs"
/// Why an edit of a post failed.
#[derive(Debug)]
pub enum EditPostError {
    /// The post changed, or was deleted, since `version` was read.
    Stale,
    /// The database failed.
    Database(sqlx::Error),
}

impl From<sqlx::Error> for EditPostError {
    fn from(error: sqlx::Error) -> Self {
        Self::Database(error)
    }
}

/// Change a post's title, if nobody changed the post since `version` was read.
pub struct EditPostTitle {
    pub id: i64,
    pub version: i64,
    pub title: String,
}

impl Query for EditPostTitle {
    type Effect = Write<Post>;
}

impl Execute<PgSource> for EditPostTitle {
    /// The new version of the post.
    type Output = i64;
    type Error = EditPostError;

    async fn execute(self, conn: &mut PgConnection) -> Result<i64, EditPostError> {
        let version: Option<i64> = sqlx::query_scalar(
            "UPDATE posts SET title = $3, version = version + 1 \
             WHERE id = $1 AND version = $2 RETURNING version",
        )
        .bind(self.id)
        .bind(self.version)
        .bind(self.title)
        .fetch_optional(conn)
        .await?; // sqlx::Error -> EditPostError::Database
        version.ok_or(EditPostError::Stale)
    }
}
```

`Db::process` returns `Result<i64, EditPostError>`, so the caller decides what each failure means in one place:

```rust title="src/wiring.rs"
pub async fn save_title(dbs: &Databases, id: i64, version: i64, title: String) -> Result<Option<i64>, sqlx::Error> {
    match dbs.primary.process(EditPostTitle { id, version, title }).await {
        Ok(new_version) => Ok(Some(new_version)),
        // Someone else won: tell the client to reload and retry.
        Err(EditPostError::Stale) => Ok(None),
        Err(EditPostError::Database(error)) => Err(error),
    }
}
```

A function that returns `EditPostError` can also `?` queries whose error is `sqlx::Error`, through the same `From` impl. Hooks don't change any of this: a [hooked handle](/en/docs/data/hooks) returns the query's error unchanged.

<Callout type="info" title="Inside a transaction">
A query run inside a [transaction](/en/docs/data/transactions) must have an error that implements [`AsSqlxError`](https://docs.rs/wakuwaku-entity/latest/wakuwaku_entity/sqlx/transaction/flow/trait.AsSqlxError.html). It tells the transaction whether the error came from the database, which may have aborted the transaction, or is the query's own, which never does. `sqlx::Error` implements it; for your own error type, return the wrapped `sqlx::Error`:

```rust title="src/queries.rs"
use wakuwaku::entity::sqlx::transaction::AsSqlxError;

impl AsSqlxError for EditPostError {
    fn as_sqlx_error(&self) -> Option<&sqlx::Error> {
        match self {
            Self::Database(error) => Some(error),
            Self::Stale => None,
        }
    }
}
```

See [errors inside a transaction](/en/docs/data/transactions#errors-inside-a-transaction).
</Callout>

## Route reads to the replica and writes to the primary

At the call site, pick the handle:

```rust title="src/wiring.rs"
pub async fn handle_requests(dbs: &Databases) -> Result<(), sqlx::Error> {
    // A profile page: a slightly stale read is fine.
    let _profile = load_profile(&dbs.replica, 7).await?;

    // Writes go to the primary.
    rename_user(&dbs.primary, 7, "Haruki".into()).await?;

    // Read your own write: the primary can read too.
    let _fresh = load_profile(&dbs.primary, 7).await?;
    Ok(())
}
```

`ReadWrite` covers every read, so the primary handle runs read queries too. Use it when a read must see a write that was just made, because a replica can lag behind the primary.

## When a write reaches a read-only handle

Pass the replica to a handler that writes:

```rust
pub async fn oops(dbs: &Databases) -> Result<bool, sqlx::Error> {
    rename_user(&dbs.replica, 7, "Haruki".into()).await
}
```

The program doesn't compile:

```text
error[E0277]: the trait bound `ReadOnly: CanWrite<User>` is not satisfied
  --> src/fails.rs:18:17
   |
18 |     rename_user(&dbs.replica, 7, "Haruki".into()).await
   |     ----------- ^^^^^^^^^^^^ the trait `CanWrite<User>` is not implemented for `ReadOnly`
   |     |
   |     required by a bound introduced by this call
   |
   = note: required for `ReadOnly` to implement `Covers<wakuwaku::wakuwaku_entity::Write<User>>`
   = note: required for `Db<SqlxSource<Postgres>, ReadOnly>` to implement `Processor<RenameUser>`
note: required by a bound in `rename_user`
```

Read the notes from the bottom up. `rename_user` needs `Processor<RenameUser>`. `Db` provides it only if its capability covers `Write<User>`, and `ReadOnly` has no `CanWrite<User>`. Calling `dbs.replica.process(RenameUser { .. })` directly fails with the same error.

If a component should write only some entities, give it a [custom capability](/en/docs/data#capabilities) instead of `ReadWrite`.

## Inject the handles into components

Handles are ordinary values, so they go into the [`ServiceBuilder`](/en/docs/core/service-builder) like any other shared dependency. `Db<PgSource, ReadOnly>` and `Db<PgSource, ReadWrite>` are different types, so register both and let each component take the ones it needs.

This [cron job](/en/docs/services/cron-jobs) finds dormant users on the replica and deactivates them on the primary:

```rust title="src/wiring.rs"
/// Deactivate users that haven't signed in for a year.
pub struct DeactivateDormantUsers {
    replica: Db<PgSource, ReadOnly>,
    primary: Db<PgSource, ReadWrite>,
}

impl Processor<CronTick> for DeactivateDormantUsers {
    type Output = ();
    type Error = sqlx::Error;

    async fn process(&self, _tick: CronTick) -> Result<(), sqlx::Error> {
        let ids = self.replica.process(DormantUsers { days: 365 }).await?;
        if !ids.is_empty() {
            self.primary.process(DeactivateUsers { ids }).await?;
        }
        Ok(())
    }
}

impl CronJob for DeactivateDormantUsers {
    const INTERVAL: CronJobInterval = CronJobInterval::AfterFinish(Duration::from_secs(60 * 60));
}
```

`DormantUsers` (`Read<User>`) and `DeactivateUsers` (`Write<User>`) are defined like the queries above. Register the handles, then build the job from both of them:

```rust title="src/wiring.rs"
pub async fn start() -> Result<(), sqlx::Error> {
    let dbs = Databases::connect(
        "postgres://app@db-primary/app",
        "postgres://app@db-replica/app",
    )
    .await?;

    let (services, cron) = ServiceBuilder::new(dbs.primary.clone())
        .push(dbs.replica.clone())
        .compose_cron_job(|s| DeactivateDormantUsers {
            replica: s.provide::<Db<PgSource, ReadOnly>, _>().clone(),
            primary: s.provide::<Db<PgSource, ReadWrite>, _>().clone(),
        })
        .start();

    // Everything else gets the handles from the builder too.
    let replica: &Db<PgSource, ReadOnly> = services.provide::<Db<PgSource, ReadOnly>, _>();
    let _profile = load_profile(replica, 7).await?;
    handle_requests(&dbs).await?;

    cron.shutdown().await;
    Ok(())
}
```

`compose_cron_job` lends the closure the builder, so a component can take any number of registered handles; it needs no `ServiceCreation` impl. A component that needs a single handle can implement [`ServiceCreation`](https://docs.rs/wakuwaku/latest/wakuwaku/services/trait.ServiceCreation.html) with that handle as its `Dep` and be registered with `cron_job`. gRPC services and event consumers have the same pair of methods; see [ServiceBuilder](/en/docs/core/service-builder). Cloning a handle only clones the pool handle, so every component can hold its own copy.

<Accordions>
  <Accordion title="Why are queries values instead of repository methods?">
    A value can be inspected before it runs. Its type carries the `Effect` the compiler checks, and a hook can describe it as a change. The same value runs on its own through a `Db` or inside a [transaction](/en/docs/data/transactions), and its `Output` and `Error` stay its own in both places. A handler that takes `D: Processor<FindUser>` depends on exactly the operations it uses, so you can replace the handle with a small fake in tests without mocking a whole repository.
  </Accordion>
  <Accordion title="Why is the capability a type parameter and not a runtime flag?">
    A runtime flag can only fail at runtime, after the write has been routed. A type parameter makes a misrouted write a compile error at the exact call that passes the wrong handle, and it costs nothing at runtime: `Db<S, C>` stores only `S`.
  </Accordion>
</Accordions>
