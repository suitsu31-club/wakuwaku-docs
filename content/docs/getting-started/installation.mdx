## Rust toolchain

wakuwaku is written in Rust edition 2024, which needs Rust 1.85 or newer. Its dependencies raise that floor. At the versions locked for wakuwaku 1.0.0-rc2, the minimum depends on the features you enable:

| Features                     | Minimum Rust | Raised by               |
| ---------------------------- | ------------ | ----------------------- |
| defaults (`grpc`, `proof`)   | 1.88         | `tonic` 0.14            |
| `redis`                      | 1.88         | `redis` 1.x             |
| `meilisearch`                | 1.89         | `uuid` (via `meilisearch-sdk`) |
| `sqlx-pg`, `sqlx-mysql`      | 1.94         | `sqlx` 0.9              |
| `iggy`                       | 1.95         | `iggy` 0.11             |

Newer releases of these dependencies may raise the minimum further, so use the latest stable toolchain:

```bash
rustup update stable
```

Generating gRPC code also needs the Protocol Buffers compiler `protoc` on your `PATH`. [Quick start](/en/docs/getting-started/quick-start) shows the build script.

## Add wakuwaku

Add `wakuwaku` with the features you need, plus `tokio` for the runtime:

```toml tab="gRPC service"
[dependencies]
wakuwaku = "1.0.0-rc2" # defaults: grpc, proof
tokio = { version = "1.53", features = ["full"] }
```

```toml tab="Events + PostgreSQL + Redis"
[dependencies]
wakuwaku = { version = "1.0.0-rc2", features = ["iggy", "sqlx-pg", "redis"] }
tokio = { version = "1.53", features = ["full"] }
```

```toml tab="Search indexer"
[dependencies]
wakuwaku = { version = "1.0.0-rc2", features = ["sqlx-pg", "meilisearch"] }
tokio = { version = "1.53", features = ["full"] }
```

```toml tab="No gRPC"
[dependencies]
# A worker that only consumes events and writes to MySQL.
wakuwaku = { version = "1.0.0-rc2", default-features = false, features = ["iggy", "sqlx-mysql"] }
tokio = { version = "1.53", features = ["full"] }
```

`entity` is enabled automatically by any of `sqlx-pg`, `sqlx-mysql`, `redis`, and `meilisearch`. Enable it alone only if you want the query and capability types without a data source, for example in a crate that defines queries for an in-memory store.

<Callout type="info" title="Release candidates">
The requirement `"1.0.0-rc2"` also accepts later release candidates and 1.0.0 itself. Write `"=1.0.0-rc2"` if you want to move to the next candidate only when you choose to.
</Callout>

## Why `wakuwaku::deps`

A type from one version of a crate is a different type from the same item in another version. If your service depended on `sqlx` 0.8 while wakuwaku uses `sqlx` 0.9, the pool you create would not be the pool `wakuwaku::entity` accepts, and the compiler error would point at a mismatch that is hard to read.

wakuwaku avoids this by re-exporting every third-party crate that appears in its public API:

| Path                         | Feature                   |
| ---------------------------- | ------------------------- |
| `wakuwaku::deps::kanau`      | always                    |
| `wakuwaku::deps::tonic`      | `grpc`                    |
| `wakuwaku::deps::iggy`       | `iggy`                    |
| `wakuwaku::deps::sqlx`       | `sqlx-pg` or `sqlx-mysql` |
| `wakuwaku::deps::redis`      | `redis`                   |
| `wakuwaku::deps::meilisearch_sdk` | `meilisearch`        |

Import from these paths instead of adding the crates yourself:

```rust
use wakuwaku::deps::kanau::processor::Processor;
use wakuwaku::deps::sqlx::PgPool;
use wakuwaku::deps::tonic::{Request, Response, Status};
```

### When you need a direct dependency

Two situations need a direct dependency anyway. In both, use a version requirement that is compatible with the one wakuwaku uses, so Cargo resolves a single copy of the crate and the types stay identical.

**Generated code and derive macros that name a crate by its path.** The code that `tonic-prost-build` generates refers to `tonic`, `tonic_prost`, and `prost`, and kanau's JSON derives expand to `::kanau::...` paths. A path through `wakuwaku::deps` cannot satisfy them:

```toml
[dependencies]
# Needed by code generated by tonic-prost-build (see Quick start).
tonic = "0.14"
tonic-prost = "0.14"
prost = "0.14"

# Needed by #[derive(JsonMessageSer, JsonMessageDe)] on event and cache bodies.
kanau = { version = "0.6", features = ["serde_json"] }
serde = { version = "1", features = ["derive"] }

[build-dependencies]
tonic-prost-build = "0.14"
```

[Defining events](/en/docs/events/defining-events#serializing-the-body) explains how message bodies are serialized.

**Extra features of a re-exported crate.** wakuwaku builds `sqlx` and `redis` with their default features off: sqlx gets only the Tokio runtime and the database driver, and redis gets only the Tokio connection and scripting support. Neither has TLS. To turn on more features, add the crate with the same major version and only the features you want. Cargo merges the features into the one copy that wakuwaku also uses:

```toml
[dependencies]
wakuwaku = { version = "1.0.0-rc2", features = ["sqlx-pg", "redis"] }
sqlx = { version = "0.9", default-features = false, features = ["tls-rustls", "migrate", "uuid"] }
redis = { version = "1", default-features = false, features = ["tokio-rustls-comp"] }
```

`sqlx::PgPool` and `wakuwaku::deps::sqlx::PgPool` are then the same type.

## Tokio runtime

wakuwaku runs on [Tokio](https://tokio.rs). Cron jobs, event consumers, and gRPC servers are spawned as Tokio tasks, and starting cron jobs outside a Tokio runtime panics. wakuwaku itself enables Tokio's `full` feature set, so adding `tokio` with `features = ["full"]` costs nothing extra. You need the direct dependency for `#[tokio::main]`, `#[tokio::test]`, and `tokio::signal`.

## Infrastructure

Each feature talks to a server that you run yourself:

| Feature       | Needs                       | Notes |
| ------------- | --------------------------- | ----- |
| `grpc`        | nothing                     | Your service is the server. |
| `iggy`        | an [Apache Iggy](https://iggy.apache.org) server | The examples connect with `iggy://iggy:iggy@localhost:8090`. Create the stream and each main topic before starting consumers. A topic is named after the partition key's super-partition name. The consumer creates only the retry topic `retry_<topic>`. |
| `sqlx-pg`     | PostgreSQL                  | Run migrations on the pool before you wrap it. |
| `sqlx-mysql`  | MySQL (InnoDB)              | Same as PostgreSQL. |
| `redis`       | Redis                       | Connect with a multiplexed connection; clones share one socket. |
| `meilisearch` | Meilisearch                 | An index is a projection of data stored elsewhere. |

The pages for each feature explain the setup in detail: [Events](/en/docs/events), [sqlx](/en/docs/data/sqlx), [Redis](/en/docs/data/redis), [Meilisearch](/en/docs/data/meilisearch).

## Check the setup

Build once to fetch and compile the dependencies:

```bash
cargo build
```

Some checks run only when the code is fully compiled. For example, a cron job with a zero interval passes `cargo check` and fails `cargo build`, so use `cargo build` or `cargo test` in CI.
