**wakuwaku** は Rust 向けの証明駆動 (proof-driven) マイクロサービスフレームワークです。使い慣れたライブラリを置き換えるものではありません。HTTP のルートは axum で、gRPC サービスは tonic で、SQL は sqlx で、それぞれのドキュメントに書かれているとおりに書きます。wakuwaku はそれらの間をつなぐグルーであり、そのつなぎ目はどれもコンパイラが検査する証明です。

- 各コンポーネントを共有の依存から組み立てるレジストリ。登録されていないものを要求するコンポーネントは作れません。
- どのエンティティを読み書きしてよいかを型で表すデータアクセスのハンドル。
- どう並べ替え、まとめ、畳み込んでよいかを型で表すイベント。
- どの検査を通ったかを型で表す検証済みの値。

wakuwaku がしないのは、プロジェクトの形を決めることです。Elixir の Phoenix や PHP の Laravel のようなフルスタックフレームワークは、それ自体がプロジェクトです。ディレクトリ構成、ジェネレーター、ルーター、ORM、ジョブの仕組み、そしてコードを埋める枠までを持ち込みます。サービスがフレームワークの想定どおりの形をしている間は、それで生産的です。wakuwaku のサービスはただの Rust のバイナリで、`main` もモジュール構成も `Cargo.toml` もあなたのものです。wakuwaku はその中の依存のひとつにすぎません。

## 使い慣れたライブラリ [#libraries-you-already-know]

各連携は、ライブラリを置き換えるものではなく、その上の薄い層です。ライブラリ自体の API、ドキュメント、サンプルはそのまま通用します。

| 書くときに使うもの | wakuwaku が加えるもの |
| --- | --- |
| `.proto` から生成した `tonic` のサーバー | 登録済みの依存から各サーバーを組み立て、ひとつのルーターにまとめて追加します。[gRPC サービス](/ja/docs/services/grpc) |
| スキーマに対してコンパイル時に検査される `sqlx` のクエリ | 読み書きするものを宣言するクエリ型。それを満たすケイパビリティを持つハンドルを通して実行します。トランザクションはフローとして書きます。[sqlx](/ja/docs/data/sqlx) |
| `redis` のコマンド | 型付きのキャッシュ・ロック・レートリミッターと、レプリカが待ち合わせられるデータ構造。どれもケイパビリティで検査されるクエリです。[Redis](/ja/docs/data/redis) |
| `meilisearch-sdk` | 型付きのフィルター、ケイパビリティで検査される検索と書き込み、テナントトークン、インデックスとそのソースとの同期。[Meilisearch](/ja/docs/data/meilisearch) |
| `iggy` のストリーム | キーごとの順序保証、代数的なバッチ処理、リトライを備えた型付きイベント。[イベント](/ja/docs/events) |
| `axum` のルート | 独自の HTTP 層はまだありません ([ロードマップ](/ja/docs/roadmap) 参照)。`ServiceBuilder` からハンドルを取り出し、ハンドラーでは他の関数と同じように `Proven` の値やケイパビリティ付きのハンドルを要求します。 |

グルーそのものは小さなものです。コンポーネントは [`kanau`](https://docs.rs/kanau) の `Processor` (またはその上に作られたトレイト) を実装したただの構造体なので、wakuwaku を必要としないコードは wakuwaku を知る必要がありません。

## 証明駆動プログラミング [#proof-driven-programming]

wakuwaku は正しさを 2 つに分けて扱います。

- **マクロな正しさ**: コンポーネント同士がどう組み合わさるか。トレイトで証明し、コンパイラが検査します。依存が登録されていないコンポーネント、読み取り専用のデータベースハンドルを通した書き込みクエリ、間隔が 0 の cron ジョブは、いずれもビルドできません。
- **ミクロな正しさ**: ひとつのコンポーネントが何をするか。ユニットテストで証明します。どのコンポーネントもただの値なので、テストではサービスを起動せずにそれを生成して直接呼び出せます。

### 証明の強さは Rust の安全性と同じ [#a-proof-is-as-strong-as-rusts-safety]

ここでいう「証明」は、Rust でいう「安全性」と同じ意味です。コンパイラは型に書かれた主張をすべて検査し、検査できないことを開発者が表明した箇所は信頼します。Rust ではその箇所が `unsafe` ブロックであり、wakuwaku では証明を *作る* コードです。`Proven<Request, Authenticated>` の信頼性は、それを生み出した述語の信頼性とまったく同じです。その述語がすべてのリクエストを通すモックの認証チェックであれば、プログラムはそのままコンパイルでき、認証済みのリクエストを要求する関数はどれもそれを受け取り、保証は失われます。常に成功する `PureVerifier` や、読み取りと宣言しておきながら SQL が書き込むクエリも、同じように健全性を壊します。述語が名前どおりの意味を持つことを、形式的に検証するものは何もありません。

これは意図した選択です。Lean のような本物の証明系の上に作ったフレームワークなら述語まで検査できますが、日々の Web 開発で使うには難しすぎます。実際には AI エージェントしか書けなくなり、それはもっと悪い結果です。チームの誰も追えないコードは、チームが信頼できるコードではありません。そもそも完全な検証でも底までは届きません。コンパイラとライブラリがすべて形式的に検証されていたとしても、ハードウェアは情報を漏らします。消費電力を観測すればデータを読み取れますし、プログラムについての証明は物理までは覆いません。どんなシステムも何かを信頼しています。Web アプリケーションにとっては Rust の水準がちょうどよいのです。検査が安いところではすべて検査し、信頼するのはそれが明示された箇所だけです。

### 間違いが一目でわかる [#mistakes-become-obvious]

証明の価値は、間違いを不可能にすることではありません。間違いを一目でわかるようにすることです。

- **一部はコンパイルエラーになります。** 登録されていない依存、読み取り専用ハンドルを通した書き込み、検証済みの値が必要な場所に渡した生の値。一覧は [コンパイラが拒否するもの](/ja/docs/core/proof-driven#what-the-compiler-rejects) にあります。
- **残りは宣言に現れます。** 読むだけでよいのに読み書き可能なハンドルを受け取るハンドラー、実際にはそうでないのに `Idempotent` と宣言したイベント、スタブから作られた `Proven`。どれもシグネチャやトレイトの impl に書かれているので、実行を追わなくても読めば気づけます。

これはどちらの読み手にも効きます。AI エージェントは数秒でフィードバックを得られます。バグが本番に届くずっと前に、コンパイラが間違った行を指します。人間のレビュアーは、1 行ずつ推論する代わりに型と宣言を読めば済みます。AI プログラミングの時代に、コードを 1 行ずつ読んで推論しようとする人はほとんどいません。wakuwaku は、それをしなくても済むように作られています。各コンポーネントが何をするかは、AI エージェントが書いて実行できるユニットテストで検査します。コンポーネントがどう組み合わさるかはコンパイラが検査し、レビューは一目で済みます。

### マクロな正しさはミクロな正しさの上に立つ [#macro-correctness-rests-on-micro-correctness]

2 つの正しさは独立していません。**マクロな正しさが本物であるのは、ミクロな正しさが本物であるとき、かつそのときに限ります。** コンパイラは、`Proven<_, Authenticated>` を要求するすべての関数がそれを受け取ることを証明します。「認証済み」が本当かどうかは述語次第であり、述語は小さなコンポーネントのひとつとしてテストで証明されます。ケイパビリティは、読み取り専用のハンドルが書き込みと *宣言された* クエリを決して実行しないことを証明します。その宣言が SQL と一致しているかどうかは、そのクエリひとつの性質です。

だから仕事はきれいに分かれます。小さな部品を徹底的にテストすれば、型システムがその正しさをサービス全体に運びます。配線が正しくても間違った部品は隠せず、間違った部品は小さいので見つけやすいのです。考え方の詳細は [証明駆動プログラミング](/ja/docs/core/proof-driven) で説明しています。

## これらと連携する理由 [#why-these-integrations]

wakuwaku が連携するインフラは、意図して少なく絞っています。連携するものにも、しないものにも理由があります。

### gRPC [#grpc]

gRPC はマイクロサービス間の通信のデフォルトの選択肢です。契約はすべての側が共有する `.proto` ファイルで、クライアントとサーバーのコードはそこから生成され、呼び出しにはデッドラインとストリームが備わっています。wakuwaku は `ServiceBuilder` から tonic のサーバーを組み立てます。公開の HTTP API が必要なら、その横に axum で書きます。[gRPC サービス](/ja/docs/services/grpc)

### cron ジョブ [#cron-jobs]

cron ジョブはトリガーです。決まった頻度で発火し、期限切れの行の削除、止まったジョブの再試行、コンシューマーに処理させるイベントの発行といった仕事を送り出します。間隔はジョブ型の定数で、ジョブはプロセス内で動くので、他のコンポーネントと同じ依存から組み立てられ、同じようにテストできます。[cron ジョブ](/ja/docs/services/cron-jobs)

### sqlx による SQL [#sql-through-sqlx]

sqlx は Rust で最良の SQL ツールキットです。素の SQL を書き、データベースのスキーマに対してコンパイル時に検査され、全体が非同期で、間に ORM を挟みません。wakuwaku はその上にケイパビリティの型を加えるだけで、SQL はあなたに任せます。データベースは PostgreSQL (`sqlx-pg`) と MySQL (`sqlx-mysql`) から選べます。

SQLite は意図してサポートしていません。SQLite はひとつのプロセスの隣にあるファイルですが、マイクロサービスはデータベースを共有するレプリカとして動きます。マイクロサービスで SQLite を使うべきではありません。[sqlx](/ja/docs/data/sqlx)

### Redis [#redis]

Redis はどこでも使われています。ほとんどのサービスはキャッシュ、ロック、レート制限のためにすでに Redis を動かしているので、組み込みでサポートしています。あるレプリカが別のレプリカの仕事の完了を待つためのデータ構造も備えています。[Redis](/ja/docs/data/redis)

### Meilisearch [#meilisearch]

Meilisearch は Rust で書かれた検索エンジンで、Rust のエコシステムに属することからサポートしています。検索とドキュメントの書き込みはクエリであり、SQL のクエリと同じように検査されます。[Meilisearch](/ja/docs/data/meilisearch)

MongoDB や Apache Cassandra といった他のデータストアは、次のメジャーバージョンでサポートされるかもしれません。それまでは、他の依存と同じようにクライアントを `ServiceBuilder` に登録して使ってください。

### Apache Iggy 上のイベント [#events-on-apache-iggy]

イベント層は、Rust で書かれたメッセージストリーミング基盤である Apache Iggy の上に作られています。これも Rust のエコシステムを理由とした選択です。イベント層が必要とするのは、パーティションに分かれた追記専用のログです。レコードは順序どおりに保存され、コンシューマーはどこまで読んだかを保存し、失敗したキーはリトライトピックへ移して、パーティションの残りを流し続けられます。キーごとの順序保証と代数的なバッチ処理は、このモデルの上で証明されています。理論上は、同じ種類のログを提供する Apache Kafka、NATS JetStream、SierraDB でも同じ設計が成り立ちます。

RabbitMQ、ZeroMQ、Redis ベースのキューは推奨せず、したがってサポートもしません。これらは順序づけられたログを保持して読ませるのではなく、メッセージを配って手放すため、イベント層が証明している順序と配信の保証をその上で成り立たせるのがはるかに難しくなるからです。[イベント](/ja/docs/events)

## クレート構成 [#crates]

| クレート          | インポート方法      | 提供するもの                                                                 |
| ----------------- | ------------------- | ---------------------------------------------------------------------------- |
| `wakuwaku`        | `wakuwaku`          | `ServiceBuilder`、gRPC の登録、cron ジョブ、Iggy コンシューマーの登録         |
| `wakuwaku-entity` | `wakuwaku::entity`  | sqlx・Redis・Meilisearch 上の、ケイパビリティで型付けされたクエリとトランザクション |
| `wakuwaku-iggy`   | `wakuwaku::iggy`    | Apache Iggy 上の型付きイベント (キーごとの順序保証と代数的なバッチ処理)        |
| `wakuwaku-proof`  | `wakuwaku::proof`   | 証明を伴うバリデーション                                                     |

これらの API に現れるサードパーティのクレート (`kanau`、`tonic`、`iggy`、`sqlx`、`redis`、`meilisearch_sdk`) は [`wakuwaku::deps`](https://docs.rs/wakuwaku/latest/wakuwaku/deps/index.html) の下に再エクスポートされています。ここからインポートすれば、バージョンが常に wakuwaku のビルドに使われたものと一致します。

## フィーチャーフラグ [#feature-flags]

| フィーチャー  | デフォルト | 有効になるもの                                                  |
| ------------- | ---------- | --------------------------------------------------------------- |
| `grpc`        | 有効       | gRPC サーバーの登録、`deps::tonic`                              |
| `proof`       | 有効       | `wakuwaku::proof`                                               |
| `iggy`        | 無効       | `wakuwaku::iggy`、Iggy コンシューマーの登録、`deps::iggy`       |
| `entity`      | 無効       | データソースなしの `wakuwaku::entity`                           |
| `sqlx-pg`     | 無効       | sqlx 経由の PostgreSQL を含む `entity`、`deps::sqlx`            |
| `sqlx-mysql`  | 無効       | sqlx 経由の MySQL を含む `entity`、`deps::sqlx`                 |
| `redis`       | 無効       | Redis を含む `entity`、`deps::redis`                            |
| `meilisearch` | 無効       | Meilisearch を含む `entity`、`deps::meilisearch_sdk`            |

cron ジョブと `ServiceBuilder` 自体は常に利用できます。よく使う組み合わせは [インストール](/ja/docs/getting-started/installation) で紹介しています。

## バージョンの状況 [#version-status]

現在のリリースは、1.0.0 の前の最後のリリース候補である **1.0.0-rc4** です。機能は凍結されており、API は 1.0.0 で出荷されるものと同じです。1.0.0 までに受け付けるのはバグ修正のみです。1.0.0 は実際のプロジェクトでの E2E テストに合格してからリリースされます。その先の計画は [ロードマップ](/ja/docs/roadmap) を参照してください。

各アイテムの API リファレンスは [docs.rs](https://docs.rs/wakuwaku) にあります。このドキュメントでは、それを使って何をどう作るかを説明します。
