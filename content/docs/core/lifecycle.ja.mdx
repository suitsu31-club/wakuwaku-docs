wakuwaku のサービスは普通の Rust バイナリです。フレームワークが握る `main` も、隠れたコンテナもありません。インフラに接続し、[`ServiceBuilder`](/ja/docs/core/service-builder) に依存を登録し、ビルダーを各レジスタセンターに順に渡し、最後に停止シグナルを待ちます。このページでは三種類のコンポーネントをすべて動かす完全な `main` を示し、各ステップの順序の理由を説明します。

## サンプルサービス [#the-example-service]

口座を管理するサービスです。

- **gRPC** サービス `Accounts` が、`AccountStore` を使って `GetBalance` に応答します。
- **イベントハンドラ** が、Iggy 上の `UserRegistered` イベントごとに `Mailer` でウェルカムメールを送ります。
- **cron ジョブ** が、1 分ごとに `SessionStore` から期限切れのセッションを削除します。

`AccountStore`、`SessionStore`、`Mailer` は、どこでも動かせるようにしたインメモリの代用品です。実際のサービスでは `Db` ハンドル、Redis ベースのストア、SMTP クライアントになりますが、それ以外のコードは変わりません。

`wakuwaku` は `tonic` を再エクスポートしていますが、`tonic-prost-build` が生成するコードは `tonic`、`tonic_prost`、`prost` を直接名前で参照するため、これらも依存に加えています (バージョンは `wakuwaku` が使うものと一致します)。詳しくは [gRPC](/ja/docs/services/grpc) を参照してください。`kanau` と `serde` の行は、イベント本体の JSON 用 derive を有効にするためのものです。[イベントの定義](/ja/docs/events/defining-events#serializing-the-body) を参照してください。

### コンポーネント [#the-components]

各コンポーネントは、`ServiceCreation` で一つの依存から作られる普通の構造体です。詳しくはそれぞれのページ ([cron ジョブ](/ja/docs/services/cron-jobs)、[イベントの消費](/ja/docs/events/consuming)、[gRPC](/ja/docs/services/grpc)) で説明しています。ここでは存在しさえすれば十分です。

```rust title="src/components.rs"
use std::collections::HashMap;
use std::hash::DefaultHasher;
use std::num::NonZeroUsize;
use std::sync::{Arc, Mutex};
use std::time::{Duration, SystemTime};

use kanau::{JsonMessageDe, JsonMessageSer};
use serde::{Deserialize, Serialize};
use wakuwaku::deps::kanau::processor::Processor;
use wakuwaku::deps::tonic::{self, Request, Response, Status};
use wakuwaku::iggy::error::HandleError;
use wakuwaku::iggy::{
    Event, EventAtomicOrdering, EventBody, EventHandler, EventTypeTag, IggySuperPartitionName,
    NonAssociative, PartitionKey,
};
use wakuwaku::{CronJob, CronTick, ServiceCreation};

use crate::proto::accounts_server::Accounts;
use crate::proto::{Balance, GetBalanceRequest};

// ---- Shared dependencies: cheap to clone, every clone shares the same state.

/// Account balances. Stands in for a database handle.
#[derive(Clone, Default)]
pub struct AccountStore {
    balances: Arc<Mutex<HashMap<u64, i64>>>,
}

impl AccountStore {
    pub fn deposit(&self, account: u64, cents: i64) {
        *self.balances.lock().unwrap().entry(account).or_default() += cents;
    }

    pub fn balance(&self, account: u64) -> Option<i64> {
        self.balances.lock().unwrap().get(&account).copied()
    }
}

/// Login sessions and when they expire.
#[derive(Clone, Default)]
pub struct SessionStore {
    expires_at: Arc<Mutex<HashMap<String, SystemTime>>>,
}

impl SessionStore {
    pub fn insert(&self, token: &str, expires_at: SystemTime) {
        self.expires_at.lock().unwrap().insert(token.to_owned(), expires_at);
    }

    pub fn contains(&self, token: &str) -> bool {
        self.expires_at.lock().unwrap().contains_key(token)
    }

    /// Remove every session that expired before `now`; return how many.
    pub fn remove_expired(&self, now: SystemTime) -> usize {
        let mut sessions = self.expires_at.lock().unwrap();
        let before = sessions.len();
        sessions.retain(|_, expires_at| *expires_at > now);
        before - sessions.len()
    }
}

/// Outgoing mail. Stands in for an SMTP client.
#[derive(Clone, Default)]
pub struct Mailer {
    sent: Arc<Mutex<Vec<String>>>,
}

impl Mailer {
    pub fn send(&self, to: &str) {
        self.sent.lock().unwrap().push(to.to_owned());
    }

    pub fn sent(&self) -> Vec<String> {
        self.sent.lock().unwrap().clone()
    }
}

// ---- Cron job: expire sessions every minute.

pub struct ExpireSessions {
    sessions: SessionStore,
}

impl ServiceCreation for ExpireSessions {
    type Dep = SessionStore;
    fn create_service(sessions: SessionStore) -> Self {
        Self { sessions }
    }
}

impl Processor<CronTick> for ExpireSessions {
    type Output = ();
    type Error = std::convert::Infallible;
    async fn process(&self, tick: CronTick) -> Result<(), Self::Error> {
        let removed = self.sessions.remove_expired(tick.fired_at);
        tracing::info!(removed, "expired sessions");
        Ok(())
    }
}

impl CronJob for ExpireSessions {
    const INTERVAL: Duration = Duration::from_secs(60);
}

// ---- Event handler: welcome mail for every new user.

#[derive(Hash)]
pub struct UserId(pub u64);

impl PartitionKey for UserId {
    type PartitionMerge = DefaultHasher;
    const SUPER_PARTITION_NAME: IggySuperPartitionName = IggySuperPartitionName("users");
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize, JsonMessageSer, JsonMessageDe)]
pub struct UserRegistered {
    pub user_id: u64,
    pub email: String,
}

impl EventBody for UserRegistered {}

impl Event for UserRegistered {
    const TYPE_TAG: EventTypeTag = EventTypeTag::new(1);
    type Key = UserId;
    type Algebra = NonAssociative;
    fn key(&self) -> UserId {
        UserId(self.user_id)
    }
    fn atomic_ordering(&self) -> EventAtomicOrdering {
        EventAtomicOrdering::Relaxed
    }
}

pub struct SendWelcomeMail {
    mailer: Mailer,
}

impl ServiceCreation for SendWelcomeMail {
    type Dep = Mailer;
    fn create_service(mailer: Mailer) -> Self {
        Self { mailer }
    }
}

impl EventHandler<UserRegistered> for SendWelcomeMail {
    const MAX_BATCH: NonZeroUsize = NonZeroUsize::new(32).unwrap();
    async fn handle(&self, run: &[UserRegistered]) -> Result<(), HandleError> {
        for event in run {
            self.mailer.send(&event.email);
        }
        Ok(())
    }
}

// ---- gRPC service: read balances.

pub struct AccountsService {
    store: AccountStore,
}

impl ServiceCreation for AccountsService {
    type Dep = AccountStore;
    fn create_service(store: AccountStore) -> Self {
        Self { store }
    }
}

#[tonic::async_trait]
impl Accounts for AccountsService {
    async fn get_balance(
        &self,
        request: Request<GetBalanceRequest>,
    ) -> Result<Response<Balance>, Status> {
        let account_id = request.into_inner().account_id;
        let cents = self
            .store
            .balance(account_id)
            .ok_or_else(|| Status::not_found("no such account"))?;
        Ok(Response::new(Balance { account_id, cents }))
    }
}
```

### `main` [#main]

```rust title="src/main.rs"
mod components;

pub mod proto {
    wakuwaku::deps::tonic::include_proto!("accounts.v1");
}

use std::sync::Arc;

use tracing_subscriber::EnvFilter;
use wakuwaku::ServiceBuilder;
use wakuwaku::deps::iggy::prelude::{Client, IggyClient};
use wakuwaku::deps::tonic::service::Routes;
use wakuwaku::deps::tonic::transport::Server;
use wakuwaku::deps::tonic::transport::server::TcpIncoming;
use wakuwaku::iggy::ConsumerConfig;

use components::{
    AccountStore, AccountsService, ExpireSessions, Mailer, SendWelcomeMail, SessionStore,
};
use proto::accounts_server::AccountsServer;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 0. Logging first, so every later step can report.
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::try_from_default_env().unwrap_or_else(|_| "info".into()))
        .init();

    // 1. Connect to infrastructure and bind the port. Any error here stops
    //    startup before a single component runs.
    let iggy = Arc::new(IggyClient::from_connection_string(
        "iggy://iggy:iggy@localhost:8090",
    )?);
    iggy.connect().await?;
    let incoming = TcpIncoming::bind("[::]:50051".parse()?)?;

    // 2. Register the shared dependencies.
    let services = ServiceBuilder::new(AccountStore::default())
        .push(SessionStore::default())
        .push(Mailer::default());

    // 3. Event consumers. `start` validates the topics and can fail.
    let (services, consumers) = services
        .iggy_consumer::<SendWelcomeMail, _, _>()
        .start(iggy.clone(), ConsumerConfig::new("shop", "accounts", vec![0]))
        .await?;

    // 4. gRPC servers. Built now, served in step 6.
    let (services, add_grpc) = services
        .grpc_service::<AccountsServer<_>, AccountsService, _>(AccountsServer::new)
        .into_router_fn();

    // 5. Cron jobs. The first run of every job happens right away.
    let (_services, cron) = services.cron_job::<ExpireSessions, _>().start();

    // 6. Serve until SIGTERM / Ctrl-C. In-flight requests finish first.
    let router = add_grpc(Server::builder().add_routes(Routes::default()));
    let served = router
        .serve_with_incoming_shutdown(incoming, shutdown_signal())
        .await;

    // 7. Drain the rest, then report how serving ended.
    consumers.shutdown().await;
    cron.shutdown().await;
    served?;
    tracing::info!("stopped");
    Ok(())
}

async fn shutdown_signal() {
    let ctrl_c = async {
        tokio::signal::ctrl_c().await.expect("install Ctrl-C handler");
    };
    #[cfg(unix)]
    let terminate = async {
        tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("install SIGTERM handler")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        () = ctrl_c => {}
        () = terminate => {}
    }
    tracing::info!("shutdown signal received");
}
```

以下、番号付きの各ステップを説明します。

## 組み立ての順序 [#order-of-construction]

ビルダーはレジスタセンターの間を *ムーブ* しながら進みます。登録メソッドはビルダーを値で受け取り、終了メソッドはそれを返すので、各ステップがそれ以前に登録された依存を参照できることは型システムが保証します。その制約の範囲で、上の順序には意図があります。

| ステップ | 何が起きるか | 失敗しうるか |
|---|---|---|
| 0. ログ | `tracing` のサブスクライバーを設定する | いいえ |
| 1. インフラ | Iggy クライアントを接続し、gRPC のポートをバインドする | はい。エラーを返す |
| 2. 依存 | `ServiceBuilder::new(..).push(..)` | いいえ |
| 3. コンシューマー | ハンドラを作る。`start` がトピックを検証し、パーティションごとにタスクを起動する | はい。エラーを返す |
| 4. gRPC | サービスを作ってサーバーで包む。まだ何も待ち受けない | いいえ |
| 5. cron ジョブ | ジョブを作る。`start` がジョブごとにタスクを起動し、各ジョブの初回実行は即座に行われる | いいえ (Tokio ランタイムの外ではパニック) |
| 6. サーブ | 停止シグナルまでリクエストを受け付ける | はい。コンポーネント起動後 |
| 7. 後片付け | コンシューマーと cron ジョブを止める | いいえ |

背後にある原則は **仕事をするものを起動する前に、失敗しうることをすべて済ませる** です。ステップ 6 の `serve` にバインドさせるのではなく、ステップ 1 で `TcpIncoming::bind` によりポートをバインドしておけば、ポートの競合は最初の cron 実行や最初のイベント消費より前にプロセスを止めます。コンシューマーを cron ジョブより先に起動するのは、その `start` がもう一つの失敗しうるステップだからです。

コンポーネントは登録メソッドの呼び出し時に作られ (`create_service` は `iggy_consumer`、`grpc_service`、`cron_job` の中で実行されます)、それぞれが自分用の `Dep` の clone を受け取ります。最後のレジスタセンターを通った後もビルダー (上の `_services`) は手元に残るので、後で実行するコードはそこから依存を `provide` できます。

## 起動時の失敗 [#startup-failures]

ステップ 1 と 3 のエラーは `?` で `main` から返され、何も実行されないままプロセスはエラーで終了します。コンシューマーの [`start`](https://docs.rs/wakuwaku-iggy/latest/wakuwaku_iggy/consumer/handler/struct.IggyConsumerRegisterCenter.html#method.start) は、タスクを起動する前に構成を検査し、[`wakuwaku::iggy::error::Error`](https://docs.rs/wakuwaku-iggy/latest/wakuwaku_iggy/error/enum.Error.html) を返します。

| バリアント | 原因 |
|---|---|
| `InvalidConfig` | `ConsumerConfig` のパーティションやリトライ間隔が空、または `poll_count == 0` |
| `MixedTopics` | 登録したイベントが一つのメイントピックを共有していない |
| `DuplicateEventType` | 同じ `EventTypeTag` に二つのハンドラが登録されている |
| `TopicNotFound` | メイントピックがストリームに存在しない |
| `PartitionNotFound` | 設定したパーティションがトピックに存在しない |
| `PartitionCountMismatch` | リトライトピック `retry_<topic>` が異なるパーティション数で存在する |
| `Iggy` | Iggy の呼び出しが失敗した |

リトライトピックがまだ存在しなければ、`start` がメイントピックと同じパーティション数で作成します。Iggy のパーティション ID は 0 始まりなので、例では `vec![0]` を消費しています。

次の二つはエラーではなくパニックになります。どちらもプログラミングの誤りで、最初の起動で見つかります。

- 同じサービス名の gRPC サーバーを二つ登録すると、ルーター関数 (`add_grpc`) がそれらを追加する時点でパニックします。
- Tokio ランタイムの外で cron ジョブを起動するとパニックします ([後述](#the-tokio-runtime))。

<Callout type="warn" title="途中で return すると、起動済みのものは中断されます">
先に起動したコンポーネントがある状態で後のステップが失敗すると、`?` で抜ける際に `ConsumerRuntime` や `CronRuntime` が drop されます。どちらも drop されると処理中の仕事を含めてタスクを **中断 (abort)** します。安全ではありますが唐突なので、失敗しうるステップを先に済ませる理由の一つになります。
</Callout>

## グレースフルシャットダウン [#graceful-shutdown]

ステップ 6 は停止シグナルまで続きます。`shutdown_signal` は Ctrl-C と、Unix ではコンテナオーケストレーターが送る `SIGTERM` で完了します。その後は、まず入口で新しい仕事の受け付けを止め、次にバックグラウンドの仕事を止めます。

1. **gRPC。** シグナルが完了すると、[`serve_with_incoming_shutdown`](https://docs.rs/tonic/0.14/tonic/transport/server/struct.Router.html#method.serve_with_incoming_shutdown) は新しい接続の受け付けを止め、開いている接続にグレースフルな終了を求め、すべての接続が閉じたら戻ります。処理中のリクエストは完了します。長時間続くストリーミング RPC は終わるまで接続を開いたままにするので、そうした RPC がある場合は `tokio::time::timeout` などで待ち時間に上限を設けてください。ポートを自分でバインドしない場合は、代わりに `serve_with_shutdown(addr, signal)` を使います。
2. **コンシューマー。** [`ConsumerRuntime::shutdown`](https://docs.rs/wakuwaku-iggy/latest/wakuwaku_iggy/consumer/struct.ConsumerRuntime.html) はすべてのパーティションタスクを中断し、停止するまで待ちます。処理中のハンドラ呼び出しはキャンセルされます。その影響は [`DeliveryMode`](/ja/docs/events/consuming) によって異なります。デフォルトの `NoEventLose` では、まだコミットされていないものはすべて同じ名前の次のコンシューマーが読み直すため、ハンドラは同じイベントを二度受け取っても問題ないようにしておく必要があります。`NoDoubleConsume` では、ポーリング済みで未処理のイベントは失われます。
3. **cron ジョブ。** [`CronRuntime::shutdown`](https://docs.rs/wakuwaku/latest/wakuwaku/services/cron_job/struct.CronRuntime.html) は新しい実行のスケジュールを止め、実行中のものが終わるのを **待ちます**。`CronRuntime` を drop した場合は中断されます。

`main` はサーブの結果を `served` に保持し、後片付けが終わってから `?` を適用します。そのため、gRPC サーバーが失敗した場合でもコンシューマーと cron ジョブはきれいに停止します。

<Callout type="info" title="猶予期間">
Kubernetes は `SIGTERM` を送った後、Pod の終了猶予期間 (デフォルトは 30 秒) を待ってからプロセスを強制終了します。最も遅い cron 実行と最も長い RPC がその期間に収まるようにするか、猶予期間を延ばしてください。
</Callout>

## Tokio ランタイム [#the-tokio-runtime]

wakuwaku は Tokio 上で動き、ランタイムを自分では作りません。作るのは `#[tokio::main]` です。タスクを起動するものはすべて、その中で呼び出す必要があります。

- `CronRegisterCenterBuilder::start` (と `CronRegisterCenter::start`) は、ランタイムの外では "there is no reactor running, must be called from the context of a Tokio 1.x runtime" で **パニック** します。
- コンシューマーの `start` と gRPC サーバーは `async` なので、そもそも await するのにランタイムが必要です。

コンポーネントは `Send` な Future を要求するので、デフォルトのマルチスレッドランタイムで動きます。コンポーネントの登録 (`create_service`、`into_router_fn`、`into_parts`) にはランタイムが不要です。だからこそ、普通のユニットテストで簡単にコンポーネントを作れます。

## ログとトレーシング [#logging-and-tracing]

フレームワークは [`tracing`](https://docs.rs/tracing) で報告します。サブスクライバーがなければ報告は捨てられるので、ステップ 0 のように何よりも先に設定してください。出力される内容は次のとおりです。

- cron の各実行は、フィールド `job` (型名) と `run` (実行回数) を持つ `cron_job` スパンの中で行われます。エラーを返した実行は `cron job failed`、パニックした実行は `cron job panicked` として記録され、ジョブはスケジュールを維持します。
- Iggy コンシューマーは、ハンドラの失敗とリトライの判断、破棄したレコード (未知の型タグ、デコードできない本体)、諦めたリトライを、`partition`、`key`、`tag` などのフィールド付きで記録します。

`EnvFilter` を使えば、レベルを実行時に選べます (例: `RUST_LOG=info,wakuwaku_iggy=debug`)。コンポーネント側も同じ `tracing` のマクロを使うので (`ExpireSessions` ジョブは削除したセッション数を記録します)、そのイベントはフレームワークのスパンの中に現れます。

<Callout type="info" title="複数レプリカで動かす場合">
すべてのレプリカがすべての cron ジョブを実行します。ジョブを冪等にするか、仕事を分割してください。[cron ジョブ](/ja/docs/services/cron-jobs) を参照してください。
</Callout>
