wakuwaku describes itself as a *proof-driven* microservice framework. The idea is simple: every property of a service should be proven by the tool that is best at proving it, as early as possible. In practice that means correctness is split in two halves.

<CorrectnessDiagram lang="en" />

| | Macro correctness | Micro correctness |
|---|---|---|
| Question | Do the components fit together? | Does each component do the right thing? |
| Examples | Every dependency is registered; a read-only handle never runs a write; a cron job has an interval; a function that needs a validated value gets one | Expired sessions are deleted; a welcome mail goes to the new user; an unknown account yields `NOT_FOUND` |
| Proven by | Traits, checked by the compiler | Unit tests |
| Fails at | `cargo build` | `cargo test` |

## Macro correctness: the compiler proves the wiring

In wakuwaku, "how things fit together" is expressed as trait bounds. A bound is a proposition, and an `impl` that satisfies it is the proof. The trait solver either finds the proof or the program does not build.

Take the [`ServiceBuilder`](/en/docs/core/service-builder). Registering a cron job that is built from a `SessionStore` requires the bound

```rust
ServiceBuilder<Head, Chain>: ProvideAt<SessionStore, Position>
```

which reads "somewhere in this builder, at some position, a `SessionStore` is registered". The builder is a list at the type level, so the compiler can check that statement. There is no runtime map, no `Any`, no downcasting, and therefore no startup panic for a missing dependency: the mistake never reaches a binary.

If you come from Spring, compare this with the application context. Spring resolves beans when the context starts, so a missing bean is reported when the application boots (`NoSuchBeanDefinitionException`). wakuwaku performs the same check while compiling, so it is reported by `cargo build`, by your editor, and by CI, before anything is deployed.

The same technique is used across the crates: capabilities on data access handles, algebra markers on events, and proof types for validated values all turn a class of runtime bugs into type errors. The [catalogue below](#what-the-compiler-rejects) lists them.

## Micro correctness: unit tests prove the behavior

Types can say that a job *has* a `SessionStore`; they cannot say that it deletes the right sessions. That is what tests are for, and wakuwaku is designed so that those tests are cheap to write.

Every component is a plain Rust value. It is created from its dependency with [`ServiceCreation::create_service`](/en/docs/core/service-builder#building-components-servicecreation), or composed from several services with the `compose_*` methods, and its behavior is a single async method:

- a cron job is a [`Processor`](https://docs.rs/kanau/latest/kanau/processor/trait.Processor.html) of `CronTick`s;
- an event handler implements `EventHandler::handle`, which has the same shape;
- a gRPC service implements the trait generated by tonic;
- a data access handle (`Db`) is a `Processor` of queries;
- a predicate is checked with `prove`, a pure check with its `PureVerifier`.

A test creates the value and calls the method. No Iggy server, no open port, no scheduler. The [Testing](/en/docs/core/testing) page shows a test for each kind of component.

## The `Processor` abstraction

The common shape comes from the [`kanau`](https://docs.rs/kanau) crate, which wakuwaku re-exports as `wakuwaku::deps::kanau`:

```rust title="kanau::processor (excerpt)"
pub trait Processor<I: Send> {
    type Output;
    type Error;

    fn process(&self, input: I) -> impl Future<Output = Result<Self::Output, Self::Error>> + Send;
}
```

A processor is a *stateful async function*: the struct holds the dependencies, and `process` turns an input into a result. You implement it with a plain `async fn`:

```rust title="src/components.rs"
impl Processor<CronTick> for ExpireSessions {
    type Output = ();
    type Error = std::convert::Infallible;
    async fn process(&self, tick: CronTick) -> Result<(), Self::Error> {
        let removed = self.sessions.remove_expired(tick.fired_at);
        tracing::info!(removed, "expired sessions");
        Ok(())
    }
}
```

If you know `tower::Service`, the differences are deliberate:

| | `tower::Service` | `Processor` |
|---|---|---|
| Receiver | `&mut self` | `&self` |
| Future | associated type `Future` (often boxed) | return-position `impl Future` (RPITIT), written as `async fn` |
| Readiness / backpressure | `poll_ready` before each `call` | none: always ready; add a semaphore or channel when you need limits |
| Sharing across tasks | clone the service, or lock it | share a reference or an `Arc` |

Taking `&self` is what lets the framework run one value from many places at once: a consumer processes several keys of a batch concurrently with the same handler (wrapped in an `Arc`), and a test can call the same value twice. The returned future must be `Send`, so components can run on Tokio's multi-threaded runtime.

`Processor` composes, too. The [write hooks](/en/docs/data/hooks) of `wakuwaku::entity` are processors that wrap another processor of the same queries, so a hooked handle is a drop-in replacement for the plain one.

## What the compiler rejects

Each row below is a mistake that does not build. Follow the link for the full explanation.

| Mistake | Error you get | Where |
|---|---|---|
| Building a component whose `Dep` was never registered | `E0277`: `(): ProvideAt<SessionStore, _>` is not satisfied | [Service builder](/en/docs/core/service-builder#reading-the-compile-errors) |
| Asking for a type registered twice without saying which | `E0283`: type annotations needed | [Service builder](/en/docs/core/service-builder#duplicate-types) |
| A cron job with a zero `CronJobInterval` | `E0080`: evaluation panicked: CronJob::INTERVAL must not be zero (`cargo build` only) | [Cron jobs](/en/docs/services/cron-jobs) |
| A write query through a read-only handle | `E0277`: `ReadOnly: CanWrite<Post>` is not satisfied | [Queries](/en/docs/data/queries) |
| A hook error handler that can itself fail | `E0271`: type mismatch resolving `<LogError as Processor<String>>::Error == Infallible` | [Hooks](/en/docs/data/hooks) |
| An `Associative` event without `EventSemigroup` (or `Idempotent` without `Eq`, `IdempotentCommutative` without `Ord`) | `E0277`: `PointsGranted: EventSemigroup` is not satisfied | [Event algebra](/en/docs/events/algebra) |
| Passing an unchecked value where `Proven<T, P>` is required | `E0308`: mismatched types | [Validation](/en/docs/validation) |
| Building a `Proven` by hand | its fields are private; only `prove`, a `PureVerifier` and the inference laws create one | [Validation](/en/docs/validation) |

Four of them, with the real compiler output (paths and help notes trimmed):

### A dependency that was never registered

```rust
let (_services, cron) = ServiceBuilder::new(Mailer) // no SessionStore registered
    .cron_job::<ExpireSessions, _>()
    .start();
```

```text
error[E0277]: the trait bound `(): ProvideAt<SessionStore, _>` is not satisfied
   |
37 |         .cron_job::<ExpireSessions, _>()
   |          ^^^^^^^^ the trait `ProvideAt<SessionStore, _>` is not implemented for `()`
   |
   = note: required for `ServiceBuilder<Mailer>` to implement `ProvideAt<SessionStore, There<_>>`
note: required by a bound in `ServiceBuilder::<Head, Chain>::cron_job`
```

`()` is the end of the list: the compiler searched every registered service and did not find a `SessionStore`.

### A write through a read-only handle

```rust
async fn on_replica(db: &Db<Memory, ReadOnly>) {
    db.process(DeletePost(1)).await.unwrap();
}
```

```text
error[E0277]: the trait bound `ReadOnly: Covers<Write<Post>>` is not satisfied
   |
32 |     db.process(DeletePost(1)).await.unwrap();
   |        ^^^^^^^ the trait `CanWrite<Post>` is not implemented for `ReadOnly`
   |
   = note: required for `ReadOnly` to implement `Covers<Write<Post>>`
   = note: required for `Db<Memory, ReadOnly>` to implement `Processor<DeletePost>`
```

### An unvalidated value

```rust
fn rename(name: Proven<String, NonEmpty>) -> String {
    name.subject().clone()
}

fn main() {
    let name = String::from("Ann");
    rename(name);
}
```

```text
error[E0308]: mismatched types
   |
27 |     rename(name);
   |     ------ ^^^^ expected `Proven<String, NonEmpty>`, found `String`
```

### A cron job with no interval

```rust
impl CronJob for Busy {
    const INTERVAL: CronJobInterval = CronJobInterval::AtLeast(Duration::ZERO);
}

let (_services, cron) = ServiceBuilder::new(SessionStore).cron_job::<Busy, _>().start();
```

```text
error[E0080]: evaluation panicked: CronJob::INTERVAL must not be zero
note: the above error was encountered while instantiating `fn CronRegisterCenter::<Busy>::new`
```

<Callout type="warn" title="This one needs cargo build">
The interval is checked by a `const` assertion that runs when the registration is instantiated, which `cargo check` (and therefore most editors) does not do. `cargo build` and `cargo test` report it. Run one of them in CI.
</Callout>

## What the types do not prove

Being precise about the limits matters as much as the guarantees:

- **External state.** Whether the Iggy topic exists, whether a configured partition exists, and whether two handlers share an event type tag are checked when the consumer [starts](/en/docs/core/lifecycle#startup-failures), not when it compiles. Two gRPC servers with the same service name make the router panic when the servers are added.
- **What a query really does.** A capability proves *routing*: code wired to a `Db<_, ReadOnly>` never issues a query *declared* as a write. It cannot prove that a query declared as a read does not write, so keep the database's own guard on replicas.
- **The moment of a proof.** A `Proven` value records that a predicate held when it was checked. If the predicate depends on a database row, the row may have changed since.
- **Business logic.** That is micro correctness, and it is the job of your [tests](/en/docs/core/testing).
